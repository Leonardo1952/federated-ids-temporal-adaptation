# Development-only unlabeled detector calibration

This document describes how the calibrations in `artifacts/calibrations/` were
produced: the frozen, dataset-specific signal scales, Page-Hinkley development
templates, and periodic budgets, derived only from the development payloads
named by the calibration-input allowlists. The calibration did not access
confirmation data, labels, targets, model states, or supervised metrics. Six
synthetic `staggered_abrupt` runs recorded in the calibration-input incident
record are not inputs. The calibration program is not part of this folder;
the calibrations are distributed pre-computed and verified by hash.

## Frozen signal definitions

The calibration follows the strategy contract (`configs/runtime/strategy_contract.yaml`).
For each nonempty development window, the global feature centroid is the
float64 mean of all feature rows. The global feature shift is the root mean
square distance between adjacent window centroids. Population shift is one
minus Jaccard similarity of the active-client sets. The first window only
initializes both baselines.

For a client, the local centroid is the float64 mean of that client's feature
rows in an active window. A local shift compares it with the last active
centroid; inactive windows do not create observations and do not reset local
history. Dataset feature scales are the empirical 0.95 quantile using NumPy's
`higher` method. The global signal is the maximum of the normalized feature
and population shifts. The local signal is the normalized local feature
shift. A zero scale maps zero shift to zero and raises a scientific error for
a positive shift. No epsilon is substituted.

Global and client-local Page-Hinkley states are independent. They use upward
detection, delta 0, lambda 1, alpha 1, minimum count 3, and strict greater-than
comparison. An alarm is recorded before its count, mean, cumulative sum, and
minimum reset. Each observation has a separate raw alarm, operational alarm,
reset, future-trigger, and future-adaptation field. The calibration
does not start triggers, training, adaptation, aggregation, or model-version
changes.

For each dataset, `B_dataset` is exactly the global operational alarm count
from development. The future confirmation schedule rule is recorded as
`floor(k * (N + 1) / (B + 1))` for `k=1..B`; B=0 means no adaptation. No
confirmation schedule is generated by the calibration.

## Access and publication

Every allowlist row is reconciled to its structural materialization inventory.
Before the NPZ archive is opened, the loader normalizes the project-relative
path, enforces the development allowlist and partition, rejects symlinks and
hard links, checks size, and verifies the full SHA-256. The archive reader
opens only `features_standardized.npy` for Gotham or `features.npy` for TON_IoT;
it does not access any other NPZ member. One feature payload pass produces
per-client/window sums and event counts. Two independent deterministic
calibration replays consume only those derived statistics.

The calibration refused existing final or incomplete output directories,
wrote to `.incomplete` result and report directories, validated their
manifests, marked them read-only, and atomically renamed each directory to
its final name. An access-control failure would have left the incomplete
report for diagnosis and prevented publication.
